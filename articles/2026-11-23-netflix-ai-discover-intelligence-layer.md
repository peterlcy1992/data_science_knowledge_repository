# Engineering AI Discover

## TL;DR

AI Discover is a new TV-app tab, available to a small group of members, where they pick a theme (e.g. "Quick Watches") and get a row of matching titles, a short note on why they fit and narrower themes to try next. Behind it is an "intelligence layer": a plan-and-execute agent harness. An LLM may propose a plan, but code validates it against declared capability contracts before running it. The harness wraps existing search and ranking systems, serves generation asynchronously, and enforces safety rules in code rather than in prompts.

## 1. Business context

Netflix recommendations have historically ranked silently from viewing history. AI Discover moves toward *steerable* discovery. The challenge is delivering generative experiences on TV without giving up speed, reliability or safety: "every turn in AI Discover ends on a screen in someone's living room", and at Netflix scale rare failures happen many times a day. The post lists seven design challenges:
- fitting LLMs into an architecture designed without them;
- keeping picks grounded in a changing catalog;
- slow, unpredictable LLMs;
- fast-changing models;
- TV constraints (remote-only input, slow app releases);
- a safety and reliability bar at scale;
- learning from what members say as well as what they watch.

## 2. Technical details

- **Flow.** The TV app sends the request to the Page Server, which hands it asynchronously to the intelligence layer. The layer has a **controller** and an **executor**.
- **Controller.** It gathers context, including real-time signals such as time of day. It picks an established plan or one drafted by an LLM planner, and validates the plan. It then retrieves from **Memory Hub** only the member details that plan needs, such as taste summaries pre-generated by **MemberLLM** (an in-house model) and member feedback.
- **Plans and capabilities.** A plan is a graph of approved steps. Each step runs a *capability*, a named, versioned unit (retrieval, ranking, generation, packaging) that declares its inputs, outputs, the context it may see and its failure behaviour. Before execution, the controller checks that every step is approved, every input has a producer, nothing loops and the plan ends in exactly one page. It checks the result again before serving.
- **Executor.** Typed outputs flow between steps through the declared contracts. Independent steps run in parallel, each with its own deadline and fallback. Some steps are single-task LLM calls, such as writing row titles or suggesting next themes.
- **Plan first, then execute.** This is used instead of a reason-act tool loop, because a loop's step count and path can't be known up front. A router decides between tested and LLM-drafted plans, and falls back to a tested plan if the planner is slow or its plan fails a check.
- **Model-agnostic.** All LLMs sit behind one interface. Model choice is a live-overridable per-task setting. Candidates are scored on the same tasks by automated checks and LLM judges before a swap, and most behaviour lives in server-side prompts and configuration, so changes need no TV app release.
- **Asynchronous generation.** A button press returns immediately and shows a "thinking" state. The server notifies the TV when the result is ready.
- **Safety in code.** Generated text is cleaned before display. The planner sees a stripped-down request and uses typed *placeholders* for parameters such as maturity rating, which the controller fills after validation; the post says this also protects against prompt injection. Each request writes a structured record (plan, steps, outcomes, rules applied) used for diagnosis, offline evaluation and replay.
- **Scope.** Members interact only through themes and tuning options such as "don't recommend". There is no free-text input or open-ended chat. Theme labels, row titles and explanations went through safety evaluations before launch.

## 3. Impact — potential & realized

**Realized:** No engagement, latency or quality metrics are reported. AI Discover is described as available to a small group of members.

**Stated next questions:** How much do members want to steer? How should stated preferences be blended with existing personalization? How do cost and latency hold up as traffic ramps, and how long will members wait? Is an error the model's, the harness's or an existing system's? Multi-turn sessions are said to need different evaluation and observability. Offline replay of past requests against a new prompt, model or rule, judged by automated checks, LLM judges and human evaluation, is already in use. A self-improving system is the long-term goal.

## Claude's Take

> Opinion, not the source's claims.

### Novelty: 3/5 — A clear reference architecture for "governed" agentic recsys, light on evidence

Plan-and-execute with contract-checked capability graphs, placeholders for sensitive parameters and async UX is a crisp, transferable pattern for putting LLMs in front of a ranking stack. The request records are the most DS-relevant piece: they make every turn replayable, which is the prerequisite for the counterfactual offline evaluation the post gestures at.

There are no numbers on engagement, latency or the A/B design. For a data scientist, the open questions they list (blending stated vs revealed preferences, waiting-time tolerance) are the interesting experiments still to come.

### Jargon buster

- **Agent harness** — the code around an LLM that decides when to call it, what it can touch, and how its output is checked.
- **Plan-and-execute agent** — the LLM drafts a whole plan up front; code validates and runs it, instead of a step-by-step tool loop.
- **Capability contract** — a declared interface (inputs, outputs, allowed context, failure behaviour) that lets a plan be verified before it runs.
- **Taste summary** — a short generated profile of what a member enjoys, precomputed by MemberLLM and used as context.
